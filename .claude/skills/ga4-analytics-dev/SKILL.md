# GA4/GSC Analytics Pipeline — Developer Reference

This is the whole pipeline end to end, in the order data actually flows. Five
tools, one registry file, one API, one UI. Read this once before touching any
of it — the pieces are small individually but the failure modes are almost
always about which stage a symptom actually belongs to.

```
ga4-provision  →  registry/sites-analytics.yaml  →  gsc-verify
   (OAuth+SA grants)   (gitignored, host-local)      (CF DNS TXT verify)
                              │
                              ▼
                  data-hub collector (cron, daily 06:17 UTC)
                              │
                              ▼
                    data-hub SQLite store
                              │
                              ▼
                  data-hub /metrics/* HTTP API  (127.0.0.1:4760)
                        │            │            │
                        ▼            ▼            ▼
              Fleet Dashboard   seo-analyst    seo-history CLI
              Analytics tab     (weekly cron,   (ad-hoc, human-
              (4754/#analytics)  files tasks)    driven, read-only)
```

## The five tools

| Tool | Path | Job | Cadence |
|---|---|---|---|
| ga4-provision | `tools/ga4-provision/` | OAuth + Service Account Viewer grants on each site's GA4 property → writes the registry | one-shot per site, human-run |
| gsc-verify | `tools/gsc-verify/` | Verifies Search Console access via Cloudflare DNS TXT record (GSC API can't grant access itself) | one-shot per site, human-run |
| data-hub collector | `tools/data-hub/src/datahub/metrics_collector.py` | Reads the registry, pulls GA4 + GSC data via each site's granted access, writes to SQLite | cron, daily 06:17 UTC (`tools/data-hub/crontab.docker`) |
| data-hub API | `tools/data-hub/src/datahub/api.py` | Serves `/metrics/*` HTTP endpoints over the stored data | always-on (`docker compose`, port 4760) |
| Fleet Dashboard | `tools/fleet-dashboard/` | Analytics tab UI — human-facing view of the API | always-on (`docker compose`, port 4754) |

Plus two consumers that read the API but aren't part of the pipeline itself:
**seo-analyst** (`tools/cron-roles/archetypes/seo-analyst/role.md.tmpl`,
per-site `sites/<domain>/ops/roles/seo-analyst.md`) — weekly automated
consumer that files real tasks — and **seo-history**
(`tools/seo-history/seo_history.py`, skill `domains-seo-history`) — ad-hoc
human CLI, read-only, no task filing.

## The registry — the one file everything keys off

`tools/data-hub/registry/sites-analytics.yaml` — **gitignored, host-local,
generated by ga4-provision, never hand-edit.** Shape:

```yaml
sites:
  americastrikes.com:
    ga4_property_id: '539753593'
    ga4_measurement_id: G-ZHHXBF92TY
    gsc_property: sc-domain:americastrikes.com
    consent_gated: false
```

- Keyed by **bare host** (no scheme) — this is the key data-hub, the API,
  and every consumer use for `?site=`.
- `ga4_measurement_id` can be `null` even when `ga4_property_id` is set —
  that means the GA4 *property* was provisioned server-side but nobody
  confirmed the client-side `gtag` is actually wired into the site's pages.
  Don't assume traffic is flowing just because the property exists; check
  `/metrics/health` for `status: "ok"` and a recent `last_fetch_at`.
- `consent_gated: true` (currently `saveusfarms.com`, `weapontester.com`)
  means GA4 undercounts — only consented visitors are captured. Every layer
  that surfaces GA4 numbers should carry this caveat through (the API's
  `/metrics/health` exposes it per-site; the dashboard and seo-history CLI
  both check it).
- **Gitignored means it doesn't exist in a fresh checkout or worktree.**
  If `/metrics/health` comes back `{"sites":{}}` after a rebuild, this file
  is missing — copy it from a checkout that has it (or re-run
  `ga4-provision`), then rebuild data-hub (see Gotchas below).
- Coverage as of this writing: 17 of 59 `sites/*` dirs are registered. The
  other 42 are either brand-neutral "COMING SOON" placeholders (correctly
  excluded — no content, nothing to measure) or **3 confirmed gaps** with
  real deployed content and no registry entry: `fishhooklabs.com`,
  `oventoheaven.com`, `vibratorporn.com`. Provision + verify those next if
  asked to close registry gaps.

## data-hub: collector, store, API

- **Collector**: `tools/data-hub/src/datahub/metrics_collector.py`, invoked
  via `python -m datahub collect-metrics` (see `tools/data-hub/src/datahub/__main__.py`).
  Reads the registry; if it's empty/missing, logs
  `"sites-analytics.yaml empty or missing, nothing to do"` and exits clean —
  that log line in `docker logs data-hub` is the tell for "registry didn't
  make it into this container."
- **GA4/GSC fetch logic**: `tools/data-hub/src/datahub/metrics/ga4.py`,
  `tools/data-hub/src/datahub/metrics/gsc.py`.
- **Store**: `tools/data-hub/src/datahub/store.py` — `query_ga4_metrics`,
  `query_gsc_metrics`, `record_pull`, `get_sources_state`. SQLite, one row
  per (site, date, grain, dim_key).
- **API**: `tools/data-hub/src/datahub/api.py:182-262` — all six
  `/metrics/*` routes in one place:
  - `GET /metrics/ga4`, `/metrics/gsc` — raw records, `?site=&since=&until=&grain=&limit=`
  - `GET /metrics/summary?site=&window=` — summed totals over N days.
    **Absence-is-not-zero**: a source key (`sessions`, `clicks`, ...) is
    only present in the response if that source has rows in the window —
    never fabricated as 0. `has_data: false` if neither source has rows.
  - `GET /metrics/top?site=&source=ga4|gsc&metric=&window=&limit=` — ranked
    dim_keys (pages for ga4, queries for gsc). Bogus `metric` name → 422,
    same absence-is-not-zero family (never silently ranks at a fabricated 0).
  - `GET /metrics/health` — per-site `{consent_gated, ga4: {status,
    last_fetch_at, ...}, gsc: {...}}`. This is the first thing to check
    when a number looks wrong — it tells you if collection is even healthy
    before you doubt the number itself.
- **Crontab**: `tools/data-hub/crontab.docker` — `collect` every 30 min
  (RSS/dataset cycle), `collect-metrics` once daily at `17 6 * * *`,
  deliberately staggered off the hour so it never races the RSS cycle.

### Deploy mechanics — data-hub is image-baked, NOT bind-mounted

Unlike the Fleet Dashboard (below), data-hub's `docker-compose.yml` builds
the image from source (`build: .`) rather than bind-mounting the repo. **Any
source change — including a fresh copy of the gitignored registry —
requires a rebuild, not a restart:**

```bash
cd tools/data-hub
docker compose build && docker compose up -d
```

A plain `restart` will NOT pick up a new `sites-analytics.yaml` or any
`.py` edit. This bit us once already (empty `/metrics/health` after adding
a fresh worktree with no registry file) — rebuild, don't restart, whenever
you touch anything under `tools/data-hub/`.

### Adding a new Analytics panel or metric — the checklist

1. If it needs a new data-hub query shape, add it to `store.py` first, then
   expose it via a new `/metrics/*` route in `api.py` (follow the
   absence-is-not-zero pattern — never fabricate a zero for missing data).
   Data-hub needs a **rebuild** (`docker compose build && up -d`), not a restart.
2. Add the corresponding client function to `analytics.js`, matching the
   existing degrade-never-throw pattern — a broken metrics call should
   render "no data" in the UI, never crash the page.
3. Add a thin route in `server.js` (clamp any numeric query params the same
   way `summary`/`top` do).
4. Wire it into `renderAnalytics()` in `app.js`, reusing `.dh-*` classes.
   Remember `esc()` on every interpolated value.
5. Ship: `server/*.js` change → `docker compose restart panel` (fleet-dashboard
   is bind-mounted, no rebuild). `server/public/*` change → nothing, just
   hard-refresh (or cache-bust `/?v=N#analytics` if testing via Playwright —
   a persistent browser context can serve stale `app.js` otherwise).
6. Verify via `curl -s http://127.0.0.1:4754/api/analytics/<route> \|
   python3 -m json.tool` after logging in (`POST /api/login` with `FD_TOKEN`
   from `/home/jesse/projects/domains/.env`, cookie-based) — see
   `fleet-dashboard-dev` skill for the exact login flow.

## Gotchas (all hit building this, don't re-hit them)

- **data-hub is image-baked, fleet-dashboard is bind-mounted** — opposite
  deploy models, opposite muscle memory. Mixing them up means either a
  wasted rebuild or a change that silently doesn't ship.
- **`docker compose up` without `--env-file ../../.env`** fails on
  fleet-dashboard with `FD_TOKEN missing` — compose needs that file for
  variable interpolation, it's not auto-loaded from the shared `.env`.
- **`prev == null` vs `!prev`** in any week-over-week delta code — `0` is a
  legitimate prior value, not an absence.
- **Absence is not zero**, everywhere in this pipeline — a missing GSC key
  in `/metrics/summary` means "not verified/no rows," not "zero traffic."
  Every layer (API, seo-analyst, seo-history, dashboard) is written to
  preserve that distinction; don't collapse it when adding new code.
- **`host.docker.internal` vs `127.0.0.1`** — fleet-dashboard's container
  reaches data-hub via `host.docker.internal:4760` (docker bridge), but a
  host-side script (like `seo-history`) uses `127.0.0.1:4760` directly.
  Wrong one silently connection-refuses depending on where the code runs.
- **The registry is gitignored** — every fresh worktree/checkout starts
  with an empty one. `/metrics/health` returning `{"sites":{}}` is the
  symptom; copying the file in + rebuilding data-hub is the fix.
